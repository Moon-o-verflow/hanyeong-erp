# 상태 전이 (state-machine.md)

㈜한결물산 사내 ERP 웹시스템

---

## 0. 이 문서의 사용법

### 0.1 단일 진실 원천 범위

상태 값의 전이 조건과 **전이별 부작용(재고 원장 기록)**의 유일한 원천입니다.
재고가 언제 움직이는지는 이 문서에만 정의됩니다. 다른 문서나 코드에서 재고 증감 시점을 별도로 판단하지 마십시오.

### 0.2 에이전트 준수 사항

1. 이 문서에 없는 전이를 구현하지 않는다. 표에 없는 상태 변경 요청은 오류로 반환한다.
2. 전이와 원장 기록은 **하나의 트랜잭션**에서 수행한다. 원장 기록 실패 시 상태 변경도 롤백한다.
3. 원장 기록 없이 상태만 바꾸거나, 상태 변경 없이 원장만 기록하는 코드를 작성하지 않는다.
4. 사전 조건 검증은 전이 실행 전에 수행하고, 실패 시 상태를 변경하지 않는다.

## 1. 사내 발주 `InternalOrderStatus`

### 1.1 상태

| 값 | 의미 |
|---|---|
| `PENDING` | 승인 대기. 아직 어떤 승인도 없음 |
| `PARTIALLY_APPROVED` | 일부 승인됨. 잔여 수량 존재 |
| `COMPLETED` | 종결. 잔여 수량 0 |
| `REJECTED` | 반려됨 |
| `CANCELED` | 지점이 전량 취소 |

### 1.2 전이표

| # | 현재 | 이벤트 | 다음 | 사전 조건 | 원장 기록 | 권한 |
|---|---|---|---|---|---|---|
| 1 | — | 발주 요청 | `PENDING` | 품목이 활성 상태, 요청 수량 ≥ 1 | 없음 | BRANCH |
| 2 | `PENDING` | 전량 승인 | `COMPLETED` | 가용 재고 ≥ 승인 수량 | `ALLOCATE +N` | ADMIN |
| 3 | `PENDING` | 부분 승인 | `PARTIALLY_APPROVED` | 가용 재고 ≥ 승인 수량 | `ALLOCATE +N` | ADMIN |
| 4 | `PARTIALLY_APPROVED` | 추가 승인 (잔여 미달) | `PARTIALLY_APPROVED` | 가용 재고 ≥ 승인 수량, 승인 수량 ≤ 잔여 | `ALLOCATE +N` | ADMIN |
| 5 | `PARTIALLY_APPROVED` | 추가 승인 (잔여 전량) | `COMPLETED` | 위와 동일 | `ALLOCATE +N` | ADMIN |
| 6 | `PENDING` | 반려 | `REJECTED` | 반려 사유 입력됨 | 없음 | ADMIN |
| 7 | `PENDING` | 지점 취소 | `CANCELED` | 자기 지점 건 | 없음 | BRANCH |
| 8 | `PARTIALLY_APPROVED` | 지점의 잔여 취소 (일부) | `PARTIALLY_APPROVED` | 취소 수량 ≤ 잔여 | 없음 | BRANCH |
| 9 | `PARTIALLY_APPROVED` | 지점의 잔여 취소 (전량) | `COMPLETED` | 취소 수량 = 잔여 | 없음 | BRANCH |
| 10 | `COMPLETED` | 승인 취소로 잔여 발생 | `PARTIALLY_APPROVED` | 승인 건이 출고 전 | `RELEASE −N` | ADMIN |

**중요 — 2번과 5번**: 잔여가 0이 되면 출고 전이라도 발주 건은 `COMPLETED`입니다. 출고 여부는 승인 건(`internal_order_approvals`)의 상태가 관리합니다. 발주 건 상태와 출고 상태를 섞지 마십시오.

**허용되지 않는 전이**
- `REJECTED` → 모든 상태. 반려는 종결이며 수정·재개할 수 없습니다 (BR-IOR-009, BR-IOR-010)
- `CANCELED` → 모든 상태
- `PENDING` → 승인 시 가용 재고 부족. 전이하지 않고 오류를 반환합니다 (BR-INV-014)

### 1.3 잔여 수량 재계산

전이 4·8·10처럼 같은 상태로 되돌아오는 경우가 있습니다. 상태 판정은 항상 전이 후 `outstanding_qty` 값을 기준으로 다시 계산하십시오.

```
outstanding_qty = 0  → COMPLETED
outstanding_qty > 0 AND approved_qty > 0 → PARTIALLY_APPROVED
outstanding_qty > 0 AND approved_qty = 0 → PENDING
```

`outstanding_qty`는 생성 컬럼이므로 직접 쓰지 않습니다.

## 2. 승인 건 `ApprovalStatus`

### 2.1 상태

| 값 | 의미 |
|---|---|
| `ALLOCATED` | 승인되어 재고가 묶임. 출고 대기 |
| `SHIPPED` | 출고 완료 |
| `CANCELED` | 승인 취소됨 |

### 2.2 전이표

| # | 현재 | 이벤트 | 다음 | 사전 조건 | 원장 기록 | 권한 |
|---|---|---|---|---|---|---|
| 1 | — | 승인 생성 | `ALLOCATED` | 가용 재고 ≥ 승인 수량 | `ALLOCATE +N` | ADMIN |
| 2 | `ALLOCATED` | 출고 완료 | `SHIPPED` | **실재고 ≥ 승인 수량** | `OUTBOUND −N (실재고), −N (할당)` | WAREHOUSE |
| 3 | `ALLOCATED` | 승인 취소 | `CANCELED` | 미출고 상태 | `RELEASE −N (할당)` | ADMIN |

**전이 2의 사전 조건이 BR-INV-010입니다.** 실재고가 부족하면 출고를 거부합니다. 부분 출고로 우회할 수 없으며, 승인 수량 전량을 출고할 수 없으면 처리 자체가 실패합니다.

**허용되지 않는 전이**
- `SHIPPED` → 모든 상태. 출고 완료 취소는 BR-SHP-003으로 **미정이며 구현 금지**입니다
- `CANCELED` → 모든 상태

### 2.3 승인 취소의 연쇄 효과

전이 3이 발생하면 상위 발주 건의 `approved_qty`가 감소하고 잔여가 늘어납니다. 발주 건 상태를 1.3의 규칙으로 재계산하십시오. `COMPLETED`였던 건이 `PARTIALLY_APPROVED`로 되돌아갈 수 있습니다(1장 전이 10).

## 3. 외부 발주 `PurchaseOrderStatus`

### 3.1 전이표

| # | 현재 | 이벤트 | 다음 | 사전 조건 | 원장 기록 | 권한 |
|---|---|---|---|---|---|---|
| 1 | — | 발주 생성·발행 | `ISSUED` | 거래처 활성, 품목행 1개 이상 | 없음 | ADMIN, PURCHASER |
| 2 | `ISSUED` | 입고 완료 | `RECEIVED` | 모든 품목행이 입고 처리됨 | 품목행별 `INBOUND +N` | WAREHOUSE |
| 3 | `ISSUED` | 발주 취소 | `CANCELED` | 입고 이력 없음 | 없음 | ADMIN |

승인 단계가 없습니다. 생성 즉시 `ISSUED`입니다 (BR-EOR-001).

**전이 2 제약**: 분할 입고가 미정(BR-RCV-002)이므로 품목행당 입고는 1회, 수량은 요청 수량 전량입니다. 부분 수량 입고 UI나 로직을 만들지 마십시오.

## 4. 재고 조정

상태를 갖지 않는 단발 이벤트입니다.

| 이벤트 | 사전 조건 | 원장 기록 | 권한 |
|---|---|---|---|
| 재고 조정 | `실재고 + delta ≥ 할당 수량` | `ADJUST ±N (실재고)` | ADMIN |

**사전 조건이 BR-INV-016입니다.** 조정 후 실재고가 현재 할당 수량 아래로 내려가면 거부하고, 현재 할당 수량과 관련 승인 건 목록을 오류 응답에 담습니다. 관리자가 승인 취소(2장 전이 3)를 선행한 뒤 다시 시도합니다.

조정 결과 실재고가 음수가 되는 경우도 동일하게 거부됩니다. 할당은 항상 0 이상이므로 위 조건이 음수 방지를 포함합니다.

## 5. 부작용 요약

재고가 움직이는 지점은 아래 5개뿐입니다. 이 표에 없는 곳에서 원장을 기록하는 코드는 오류입니다.

| 발생 지점 | 원장 유형 | 실재고 | 할당 |
|---|---|---|---|
| 사내 발주 승인 | `ALLOCATE` | — | +N |
| 출고 완료 | `OUTBOUND` | −N | −N |
| 승인 취소 | `RELEASE` | — | −N |
| 외부 발주 입고 완료 | `INBOUND` | +N | — |
| 재고 조정 | `ADJUST` | ±N | — |

`OPENING`은 이관 시 1회만 발생하며 운영 전이에 포함되지 않습니다 (BR-MIG-004).

**지점 재고는 이 표와 무관합니다.** 출고 완료가 지점 재고를 증가시키지 않습니다. 지점 재고는 담당자의 수기 입력으로만 변합니다 (BR-BRS-001).

## 6. 동시성 처리

BR-INV-011의 선착순 원칙 구현 방식입니다.

가용 재고를 검증하는 전이(1장 2~5번, 2장 1번), 실재고를 검증하는 전이(2장 2번), 재고 조정은 **품목 단위 직렬화**가 필요합니다.

### 6.1 절차

```
1. 트랜잭션 시작
2. SELECT pg_advisory_xact_lock(1001, :itemId)
3. v_item_stock 재조회
4. 사전 조건 검증 (해당 전이의 조건)
5. inventory_ledger INSERT
6. 상태 UPDATE
7. 커밋 — 락 자동 해제
```

### 6.2 금지 사항

- **`SELECT ... FOR UPDATE`를 쓰지 마십시오.** Neon 풀러(PgBouncer transaction 모드) 환경에서 신뢰할 수 없습니다
- **락을 명시적으로 해제하지 마십시오.** `pg_advisory_xact_lock`은 트랜잭션 종료 시 자동 해제됩니다. `pg_advisory_unlock`을 호출하는 코드는 오류입니다
- **3단계를 생략하지 마십시오.** 요청 본문이나 화면에서 넘어온 재고 값을 검증에 사용하는 구현은 위반입니다. 표시된 값은 항상 낡은 값입니다
- **HTTP 드라이버(`neon()`)를 쓰지 마십시오.** 2~7단계가 한 트랜잭션이어야 하므로 WebSocket `Pool`이 필수입니다
- **Edge runtime에 두지 마십시오.** 해당 Route Handler는 `export const runtime = 'nodejs'`를 명시합니다

### 6.3 락 순서

한 트랜잭션에서 두 개 이상의 품목을 잠가야 하는 경우(외부 발주 다품목 입고)는 **`item_id` 오름차순**으로 잠급니다. 순서를 지키지 않으면 교착이 발생합니다.

### 6.4 성능

월 150건 규모이므로 경합 비용은 문제가 되지 않습니다. 락 범위를 좁히기 위한 최적화를 시도하지 마십시오. 락 대기가 임계치를 넘으면 `CONCURRENCY_CONFLICT`를 반환하고 사용자에게 재시도를 안내합니다.

## 7. 수치 트레이스

구현 검증용입니다. `acceptance-tests.md` 작성 시 이 시나리오를 기준으로 삼으십시오.

### 7.1 부분 승인 → 미결 → 2차 승인

품목 A, 초기 실재고 100 / 할당 0 / 가용 100

| 단계 | 이벤트 | 실재고 | 할당 | 가용 | 발주 상태 | 잔여 |
|---|---|---|---|---|---|---|
| 1 | 강남지점이 100 요청 | 100 | 0 | 100 | `PENDING` | 100 |
| 2 | 관리자가 50 승인 | 100 | 50 | 50 | `PARTIALLY_APPROVED` | 50 |
| 3 | 창고가 50 출고 완료 | 50 | 0 | 50 | `PARTIALLY_APPROVED` | 50 |
| 4 | 외부 발주 30 입고 완료 | 80 | 0 | 80 | `PARTIALLY_APPROVED` | 50 |
| 5 | 관리자가 미결 30 승인 | 80 | 30 | 50 | `PARTIALLY_APPROVED` | 20 |
| 6 | 지점이 잔여 20 취소 | 80 | 30 | 50 | `COMPLETED` | 0 |
| 7 | 창고가 30 출고 완료 | 50 | 0 | 50 | `COMPLETED` | 0 |

6단계에서 발주가 `COMPLETED`가 되지만 5단계 승인 건은 아직 `ALLOCATED`입니다. 7단계에서 `SHIPPED`가 됩니다.

### 7.2 승인 경합

품목 B, 실재고 20 / 할당 0 / 가용 20

| 단계 | 이벤트 | 결과 |
|---|---|---|
| 1 | 관리자 甲이 수원지점 건 20 승인 | 성공. 할당 20, 가용 0 |
| 2 | 관리자 乙이 성남지점 건 20 승인 | **실패.** "가용 재고 부족, 현재 가용 0" |
| 3 | 관리자 乙이 성남지점 건을 승인하지 않고 대기 | 성남 건은 `PENDING` 유지 |

2단계에서 시스템이 자동으로 0개 부분 승인을 하지 않습니다 (BR-INV-014).

### 7.3 조정 차단

품목 C, 실재고 100 / 할당 80 / 가용 20

| 단계 | 이벤트 | 결과 |
|---|---|---|
| 1 | 실사 결과 50으로 조정 시도 (delta −50) | **실패.** `50 < 80`. 할당 80과 관련 승인 건 목록 반환 |
| 2 | 관리자가 승인 건 40을 취소 | 할당 40, 가용 60 |
| 3 | 다시 50으로 조정 시도 (delta −50) | 성공. 실재고 50, 할당 40, 가용 10 |

# 비즈니스 규칙 명세 (business-rules.md)

㈜한결물산 사내 ERP 웹시스템

---

## 0. 이 문서의 사용법

### 0.1 단일 진실 원천 범위

이 문서는 **업무 규칙(무엇이 허용되고 무엇이 금지되며 어떤 계산을 따르는가)**의 유일한 원천입니다.
다른 문서는 규칙을 재서술하지 않고 ID로 참조만 합니다.

| 문서 | 담당 범위 |
|---|---|
| `business-rules.md` (이 문서) | 업무 규칙, 계산식, 금지 조건 |
| `glossary.md` | 한국어 도메인 용어 ↔ 영문 식별자 |
| `data-model.md` | 테이블·컬럼·제약·인덱스 |
| `state-machine.md` | 상태 전이표와 전이별 부작용 |
| `permissions.md` | 권한 × 리소스 × 액션 매트릭스 |
| `api-spec.md` | 엔드포인트, 요청/응답 스키마, 에러 코드 |
| `acceptance-tests.md` | Given-When-Then 시나리오 (각 항목에 BR-ID 태그) |

규칙과 구현이 어긋날 경우 이 문서가 우선합니다. 구현을 바꾸십시오.

### 0.2 규칙 ID 체계

```
BR-{DOMAIN}-{NNN}
```

| DOMAIN | 범위 |
|---|---|
| `ITM` | 품목 마스터 |
| `INV` | 본사 재고, 재고 원장, 재고 조정 |
| `IOR` | 사내 발주 (Internal Order, 지점 → 본사) |
| `EOR` | 외부 발주 (External Order, 본사 → 공급사) |
| `RCV` | 입고 (Receiving) |
| `SHP` | 출고 (Shipping) |
| `BRS` | 지점 재고 (Branch Stock) |
| `SUP` | 거래처(공급사) |
| `AUT` | 권한·인증 |
| `RPT` | 조회·리포트 |
| `MIG` | 데이터 이관·일괄 업로드 |

- 번호는 도메인별 001부터 부여하며 **재사용하지 않습니다.** 폐기된 규칙은 번호를 비우지 않고 `상태: 폐기`로 남깁니다.
- 번호 사이를 비워 두어도 무방합니다. 순서는 의미를 갖지 않습니다.

### 0.3 상태 태그

| 태그 | 의미 | 구현 가능 여부 |
|---|---|---|
| `확정` | 고객이 상담에서 직접 확인한 규칙 | 구현 |
| `제안` | 개발사가 정하고 고객 확인 없이 진행하기로 한 규칙 | 구현 |
| `TODO(고객확인)` | 확정되지 않았으며 임의 판단이 금지된 항목 | **구현 금지** |
| `폐기` | 더 이상 유효하지 않음 | 구현 금지 |

### 0.4 에이전트 준수 사항

`AGENTS.md`에 다음을 반드시 명시하십시오.

1. 이 문서에 없는 업무 규칙을 추론해 구현하지 말 것.
2. `TODO(고객확인)` 태그가 붙은 규칙에 해당하는 코드는 생성하지 말고 작업을 중단하고 보고할 것.
3. 규칙이 적용되는 코드에는 해당 BR-ID를 주석으로 남길 것. (예: `// BR-INV-010`)
4. 규칙 간 모순을 발견하면 임의로 해소하지 말고 보고할 것.

### 0.5 규칙 항목 서식

```
### BR-XXX-NNN · 규칙명
- 상태:
- 근거:
- 규칙:
- 예외:
- 관련:
```

- **근거**: `확정`은 고객 발언을 짧게 인용합니다. `제안`은 판단 이유를 한 줄로 적습니다.
- **규칙**: 조건과 동작을 단정형으로 씁니다. "~하는 것이 좋다" 같은 표현을 쓰지 않습니다.
- **관련**: 다른 BR-ID, 테이블명, 상태명을 적습니다.

## 1. ITM — 품목 마스터

### BR-ITM-001 · 신규 등록 필수 입력 항목
- 상태: 확정
- 근거: 고객 — 절대 빈칸으로 두면 안 되는 항목으로 4개를 지정함
- 규칙: 품목 신규 등록 시 다음 4개 항목은 비어 있을 수 없다. 하나라도 비면 저장을 거부한다.
  - 자체 품목코드, 상품명, 매입단가, 지점 공급단가
- 예외: 바코드 번호, 카테고리, 규격, 최소 재고 수량, 비고는 선택 입력이다.
- 관련: `items` 테이블, BR-MIG-002

### BR-ITM-002 · 품목코드 승계 및 자동 채번
- 상태: 확정
- 근거: 고객 — 기존 코드 승계 후 신규 등록분부터 자동 채번(A안) 선택
- 규칙: 이관된 기존 품목 약 500건은 엑셀의 코드를 그대로 사용한다. 신규 등록 시에는 사용자가 코드를 입력할 수 없으며, 시스템이 채번한다.
- 관련: BR-ITM-003, BR-MIG-001

### BR-ITM-003 · 자동 채번 규칙
- 상태: 제안
- 근거: 기존 코드가 1001부터의 연속 정수이므로 별도 규칙 없이 이어받는 것이 혼선이 적음
- 규칙: 채번 값은 `현재 존재하는 품목코드 중 정수로 해석 가능한 최대값 + 1`이다. 정수로 해석 불가한 코드는 최대값 계산에서 제외한다.
- 예외: 동시 등록 경합에 대비해 채번은 DB 유니크 제약과 재시도로 보장한다. 애플리케이션 메모리에 최대값을 캐시하지 않는다.
- 관련: BR-ITM-004

### BR-ITM-004 · 품목코드 불변
- 상태: 제안
- 근거: 발주·재고 원장이 품목코드를 참조하므로 변경 시 이력 추적이 끊김
- 규칙: 품목코드는 전체에서 유일하며 등록 후 수정할 수 없다. 잘못 등록된 품목은 비활성 처리하고 새로 등록한다.
- 관련: `items.item_code`

### BR-ITM-005 · 규격 필드 분할
- 상태: 제안
- 근거: 고객이 규격/단위 분리에 동의했으며, 샘플 데이터 확인 결과 실제로는 4개 요소가 한 칸에 들어 있음
- 규칙: 기존 규격 텍스트를 다음 4개 필드로 분할해 저장한다.

  | 필드 | 예시 (`500ml 12입/박스`) | 예시 (`30롤/팩`) | NULL |
  |---|---|---|---|
  | 낱개 규격 | `500ml` | (없음) | 허용 |
  | 낱개 단위 | `개` | `롤` | 허용 |
  | 입수 | `12` | `30` | 불가, 기본값 1 |
  | 포장 단위 | `박스` | `팩` | 불가 |

- 예외: 낱개 규격과 낱개 단위가 없는 품목이 존재한다. 입수와 포장 단위는 항상 값을 갖는다.
- 관련: BR-ITM-006, BR-MIG-003

### BR-ITM-006 · 재고 관리 단위
- 상태: 확정
- 근거: 고객 — "재고 100은 100박스를 의미", "지점도 박스 단위로만 발주"
- 규칙: 모든 재고 수량과 발주 수량은 **포장 단위(박스) 기준 정수**다. 낱개 단위 수량은 시스템 어디에도 저장하지 않는다.
- 예외: 입수 정보는 화면 표시용 참고 값이며 어떤 계산에도 사용하지 않는다. 박스↔낱개 환산 기능은 구현하지 않는다.
- 관련: BR-INV-002, BR-IOR-002

### BR-ITM-007 · 최소 재고 수량의 용도
- 상태: 제안
- 근거: 마스터에 필드는 존재하나 활용 방식이 상담에서 논의되지 않음. 1차는 표시로 한정
- 규칙: 재고 현황 리포트에서 `실재고 < 최소 재고 수량`인 품목을 미달로 표시한다. 알림 발송, 자동 발주, 발주 차단에는 사용하지 않는다.
- 관련: BR-RPT-001

### BR-ITM-008 · 단가 필드
- 상태: 확정
- 근거: 고객 제시 엑셀 열 구성
- 규칙: 품목은 매입단가와 지점 공급단가를 각각 갖는다. 단가는 원 단위 정수로 저장한다.
- 예외: 단가 변경 이력 보관은 1차 범위에 포함하지 않는다.
- 관련: BR-AUT-003, BR-EOR-003

## 2. INV — 재고 및 재고 원장

### BR-INV-001 · 원장 기반 재고 산출
- 상태: 제안
- 근거: 고객의 최초 페인포인트가 재고 수량 불일치임. 카운터 직접 갱신 방식은 불일치 발생 시 원인 추적이 불가능함
- 규칙: 재고는 **append-only 재고 원장(`inventory_ledger`)의 합계로만 산출**한다. 어떤 코드도 재고 수량을 직접 UPDATE하지 않는다.
- 예외: 조회 성능을 위한 캐시 컬럼을 둘 수 있으나, 원장이 항상 우선이며 캐시는 원장으로부터 재계산 가능해야 한다.
- 관련: BR-INV-003

### BR-INV-002 · 재고 수량 3종 정의
- 상태: 확정
- 근거: 고객 — 신규 발주자에게 가용 재고가 20으로 보이는 방식 선택
- 규칙: 품목별 재고를 다음 세 가지로 구분한다.
  ```
  실재고   = 창고에 물리적으로 존재하는 수량
  할당     = 승인되었으나 아직 출고되지 않은 수량
  가용재고 = 실재고 - 할당
  ```
- 예외: 세 값 모두 음수가 될 수 없다.
- 관련: BR-INV-010, BR-INV-012, BR-INV-013

### BR-INV-003 · 원장 트랜잭션 유형
- 상태: 확정
- 근거: 상담에서 확정된 입고·승인·출고·취소·조정 시점을 원장 유형으로 정리한 것
- 규칙: 원장 트랜잭션은 다음 6종뿐이다. 이 외의 유형을 추가하지 않는다.

  | 유형 | 발생 시점 | 실재고 | 할당 |
  |---|---|---|---|
  | `INBOUND` (입고) | 창고 입고 완료 처리 | +N | — |
  | `ALLOCATE` (할당) | 사내 발주 승인 | — | +N |
  | `OUTBOUND` (출고) | 창고 출고 완료 처리 | −N | −N |
  | `RELEASE` (할당 해제) | 승인 취소 / 반려 / 미결 취소 | — | −N |
  | `ADJUST` (조정) | 관리자 재고 조정 | ±N | — |
  | `OPENING` (초기 이관) | 시스템 오픈 시 1회 | +N | — |

- 예외: `OPENING`은 데이터 이관 시에만 생성되며 운영 중에는 생성될 수 없다.
- 관련: BR-MIG-004

### BR-INV-004 · 재고의 적용 범위
- 상태: 확정
- 근거: 고객 — "재고 수량은 본사 창고의 재고만을 의미합니다"
- 규칙: 재고 원장과 실재고·할당·가용재고는 **본사 창고에만** 적용된다. 지점 재고는 별도 체계로 관리하며 원장에 기록하지 않는다.
- 관련: BR-BRS-001

### BR-INV-010 · 실재고 부족 시 출고 차단
- 상태: 확정
- 근거: 고객 — "음수 재고를 허용하지 않고, 출고를 막는 것이 좋습니다"
- 규칙: 출고 완료 처리 시점에 `실재고 < 출고 수량`이면 처리를 거부하고 오류를 반환한다. 실재고는 어떤 경우에도 음수가 될 수 없다.
- 예외: 부분 출고로 우회할 수 없다. 승인 수량 전체를 출고할 수 없으면 처리 자체를 거부한다.
- 관련: BR-SHP-001, BR-INV-016

### BR-INV-011 · 동시 처리 경합
- 상태: 확정
- 근거: 고객 — "선착순으로 처리". 단, 할당 도입에 따라 경합 지점이 출고에서 승인으로 이동함
- 규칙: 동일 품목에 대한 동시 요청은 선착순으로 처리한다. 먼저 커밋된 트랜잭션이 우선하며, 이후 트랜잭션은 갱신된 재고를 기준으로 재검증한다.
- 예외: 할당 도입(BR-INV-013)으로 승인 시점에 수량이 확보되므로 출고 시점의 경합은 정상 흐름에서 발생하지 않는다. 실제 경합은 승인 시점에서 발생하며 BR-INV-014를 따른다.
- 관련: BR-INV-013, BR-INV-014

### BR-INV-012 · 권한별 재고 노출 범위
- 상태: 확정
- 근거: 고객 — "신규 발주자는 실제 가용 수량에 대한 정보만 보게 되어"
- 규칙: 지점 권한 사용자에게는 **가용 재고만** 노출한다. 실재고와 할당 수량은 응답에 포함하지 않는다. 관리자·구매·창고 권한은 세 값을 모두 조회한다.
- 예외: 필터링은 화면이 아닌 API 응답 단계에서 수행한다. 지점 권한 응답에 실재고 값을 담은 뒤 화면에서 숨기는 구현을 금지한다.
- 관련: BR-AUT-002

### BR-INV-013 · 할당 발생 시점
- 상태: 확정
- 근거: 고객 — B안 선택, "실제로 나갈 것이 확정된 수량만 반영"
- 규칙: 할당은 **본사 관리자가 사내 발주를 승인하는 시점**에 발생한다. 지점이 발주를 요청한 단계에서는 가용 재고를 차감하지 않는다.
- 예외: 여러 지점이 동일 품목을 동시에 요청 중일 때 요청 합계가 가용 재고를 초과할 수 있다. 이는 정상 상태이며 승인 단계에서 조정된다.
- 관련: BR-IOR-003, BR-INV-014

### BR-INV-014 · 승인 시 가용 재고 부족
- 상태: 확정
- 근거: 고객 — A안 선택, "관리자가 부분 승인 여부를 다시 판단할 수 있어"
- 규칙: 승인 수량이 가용 재고를 초과하면 승인을 실패 처리하고 "가용 재고 부족"과 현재 가용 수량을 반환한다.
- 예외: 시스템이 자동으로 부분 승인하지 않는다. 관리자가 수량을 조정해 다시 승인해야 한다.
- 관련: BR-IOR-004

### BR-INV-015 · 재고 조정
- 상태: 확정
- 근거: 고객 — "재고 조정 기능은 1차 범위에 필요하다고 생각합니다"
- 규칙: 관리자 권한 사용자는 품목별 실재고를 직접 조정할 수 있다. 조정 시 사유 입력은 필수이며, 조정 이력은 원장에 `ADJUST` 유형으로 영구 보관한다.
- 예외: 창고·구매·지점 권한은 조정할 수 없다.
- 관련: BR-INV-016, BR-INV-017, BR-AUT-004

### BR-INV-016 · 조정 하한
- 상태: 확정
- 근거: 고객 — A안 선택, "승인된 수량 아래로는 내릴 수 없도록"

- 예외: 잔여 수량은 음수가 될 수 없다. 누적 승인과 누적 취소의 합이 요청 수량을 초과하는 처리를 거부한다.

### BR-IOR-007 · 미결 건 지점 취소

## 9. RPT — 조회 및 리포트

### BR-RPT-001 · 조회 필터

- 근거: 고객 제시 5종 + 발주 번호 + 개발사 제안 2종 동의
- 규칙: 발주 내역과 재고 조회 화면은 다음 8종 필터를 제공한다. 복수 필터는 AND로 결합한다.
  1. 날짜 기간
  2. 지점명
  3. 발주 진행 상태
  4. 품목명
  5. 거래처명
  6. 발주 번호
  7. 담당자명
  8. 규격
- 예외: 지점 권한 사용자에게 지점명 필터는 자기 지점으로 고정된다.
- 관련: BR-BRS-002

## 10. MIG — 데이터 이관

### BR-MIG-001 · 엑셀 일괄 업로드
- 상태: 확정
- 근거: 고객 — "1차 구축 범위에 필수적으로 포함되어야 한다고 생각합니다"
- 규칙: 관리자는 정해진 양식의 엑셀 파일로 품목 정보와 초기 재고를 일괄 등록할 수 있다.
- 예외: 업로드 대상 약 500건 기준이며 대용량 스트리밍 처리를 구현하지 않는다.

### BR-MIG-002 · 업로드 검증
- 상태: 제안
- 근거: 부분 반영은 재고 불일치의 원인이 되므로 전건 검증 후 일괄 반영이 안전함
- 규칙: 업로드 시 전체 행을 먼저 검증한다. 한 행이라도 오류가 있으면 어떤 행도 반영하지 않고, 행 번호와 사유를 목록으로 반환한다.
- 예외: 검증 항목은 필수 항목 누락(BR-ITM-001), 품목코드 중복, 수량·단가의 숫자 형식 위반이다.

### BR-MIG-003 · 규격 파싱
- 상태: 제안
- 근거: 기존 데이터가 `500ml 12입/박스`, `30롤/팩` 형태이며 자동 분할이 필요함
- 규칙: 규격 텍스트를 BR-ITM-005의 4개 필드로 파싱한다.
  - `/` 앞뒤를 분리해 뒤쪽을 포장 단위로 한다.
  - 앞쪽에서 `숫자 + 입` 패턴이 있으면 그 숫자를 입수로 한다.
  - `숫자 + 입` 패턴이 없고 `숫자 + 문자` 형태이면 숫자를 입수, 문자를 낱개 단위로 한다.
  - 남은 앞쪽 텍스트를 낱개 규격으로 한다.
- 예외: 파싱 실패 행은 업로드를 중단시키지 않는다. 4개 필드를 비운 채 원문을 보존하고 `파싱 실패` 플래그를 세워 관리자가 수기 보정한다.
- 관련: BR-MIG-002

### BR-MIG-004 · 초기 재고 기록
- 상태: 제안
- 근거: 초기 재고를 조정으로 기록하면 운영 중 발생한 조정과 구분되지 않아 원인 추적이 어려움
- 규칙: 초기 재고는 원장에 `OPENING` 유형으로 기록한다. `ADJUST`를 사용하지 않는다.
- 예외: `OPENING`은 시스템 오픈 시 1회만 생성 가능하다.
- 관련: BR-INV-003
